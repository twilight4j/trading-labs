# 수집 스케줄과 화면에서의 실행

## 한 프로세스가 서비스하고 수집한다

`labs-api serve` 하나가 API 와 수집 스케줄러를 함께 돌립니다. 스케줄러만 따로 띄우는 `market-data serve` 는 없앴습니다(2026-10-04).

- **이유:** trading-ui 의 데이터 수집 화면이 스케줄을 켜고 끄고, 지금 실행하고, 실행 중인지 봅니다. 스케줄러가 다른 프로세스면 이 상태를 파일로 주고받아야 합니다. 한 프로세스면 "실행 중"과 "두 번 돌리지 않기"가 메모리 안의 상태로 끝납니다.
- **주의:** `labs-api` 를 다시 띄우면 돌고 있던 수집이 중단됩니다. 컨센서스는 약 10분 걸리니 실행 중에는 다시 띄우지 않습니다. 일봉·재무는 끝난 파티션이 남고 다음 실행이 이어서 채웁니다.
- **두 번 띄우지 않습니다.** `labs-api` 를 둘 띄우면 같은 시각에 수집이 두 번 돕니다.

| 작업 | 스케줄 | 화면에서 실행 | 하는 일 |
|---|---|---|---|
| `daily` 일봉 갱신 | 평일 18:30 | 가능 | 빠진 거래일을 모두 채웁니다 |
| `consensus` 컨센서스 | 토요일 09:00 | 가능 | 오늘 날짜 스냅샷 ([적정시총](valuation.md)) |
| `fundamentals` 재무 주요계정 | 없음 | 가능 | 올해 보고서 재수집. OpenDART 일일 한도에 걸리면 `quota_exceeded` 로 멈추고 끝난 파티션은 남습니다 |
| `adjusted` 수정주가 | 없음 | 불가 | 종목·기간을 정해야 해서 `market-data prices rebuild-adjusted` 로만 실행합니다. 화면은 기록만 보입니다 |

시각은 `Settings.schedule_*`, `Settings.consensus_schedule_*` 가 정합니다(`collector.ingestion.scheduler.schedules`).

## 일봉 갱신 규칙

`market-data update` 와 스케줄·화면 실행 모두 `IngestionService.catch_up` 을 부릅니다.

- **빠진 날을 모두 채웁니다.** 마지막 거래일 파티션 다음 날부터 평일마다 하루씩 받습니다. 예전에는 실행 한 번에 하루치만 받아서, 한 번 놓치면 그 뒤로 계속 하루 늦었습니다(2026-10-01 18:30 실행이 09-30 을 채움).
- **휴장일은 저장하지 않습니다.** pykrx 는 휴장일에도 전 종목을 거래량·시총 0 으로 돌려줍니다. 거래량이 하나도 없는 날은 `skipped` 로 돌려주고 raw·curated 어느 쪽에도 쓰지 않습니다. 받은 날이 휴장일뿐이면 `skipped` 실행 기록 하나를 남깁니다(화면에 "왜 안 들어왔는지"가 보이게).
  - 그 전에 쌓인 휴장일 파티션이 2010년부터 2026-09-25 까지 248일 있었고, 2026-10-04 에 치웠습니다(일봉 파티션 4,371 → 4,123). 읽는 쪽은 그래도 건너뜁니다 — 적정주가·컨센서스 대상(`read_latest_prices`), 백테스트 가격(0 가격을 버림), 유니버스 조회(`list_universe`). 유니버스 조회는 2026-10-04 까지 건너뛰지 않아, 기준일이 휴장일이면 0종목이 나왔습니다.
  - 치우는 명령은 `market-data prices prune-closed-days` 입니다. 대상만 보여 주고, `--apply` 를 붙여야 일봉·유니버스 스냅샷·raw 의 그 날짜 폴더를 지웁니다. 지운 날짜는 `metadata/maintenance/` 에 남깁니다. 다시 받아도 저장되지 않으므로 되살릴 것이 없는 데이터입니다.
- **장 마감 전에는 오늘을 받지 않습니다.** 스케줄 시각(18:30) 전에 실행하면 어제까지만 채웁니다(`settled_date`). 장중에는 pykrx 가 그 시점 값을 주는데, 한 번 저장한 날은 다시 받지 않기 때문입니다.

## 스케줄 켜고 끄기

켜짐·꺼짐은 `metadata/collection/schedule.json` 에 둡니다. 없으면 켜짐입니다. 재시작해도 유지됩니다.

꺼진 스케줄도 시각이 되면 불리고, 그때 꺼져 있으면 건너뜁니다(`CollectionJobs.run_scheduled`). 스케줄러의 일시정지 상태와 파일을 따로 맞출 필요가 없게 하려는 것입니다.

## 같은 작업은 한 번에 하나

작업마다 한 번에 하나만 돕니다. 화면에서 실행한 작업이 도는 중에 스케줄 시각이 오면 그 스케줄은 건너뜁니다. 화면에서 다시 누르면 `409 conflict` 입니다. 서로 다른 작업은 함께 돌 수 있습니다.

## API

모두 `/api/labs/v1/collection` 아래이고 토큰이 필요합니다([적정시총](valuation.md)의 인증 규칙과 같습니다). 요청·응답 모양의 원본은 코드(`src/valuation/collection.py`)와 서버의 `/docs` 입니다.

| 경로 | 하는 일 |
|---|---|
| `GET /status` | 스케줄러 가동 여부, 작업별 스케줄·다음 실행·실행 중·마지막 실행, 일봉 마지막 거래일과 컨센서스 스냅샷 날짜, 최근 실행 30건 |
| `POST /jobs/{job}/run` | 작업을 백그라운드로 시작합니다(`202`). 실행 중이면 `409`, `adjusted` 는 `400` |
| `PUT /jobs/{job}/schedule` | `{"enabled": bool}`. 스케줄이 있는 `daily`·`consensus` 만 |

- 실행 기록은 `metadata/ingestion_runs` 의 JSON 입니다. 실행이 **끝날 때** 남으므로 "실행 중"은 기록이 아니라 프로세스 안의 상태에서 나옵니다.
- 기록 파일이 4,400개가 넘어, 디렉터리가 바뀔 때만 다시 읽습니다(첫 조회 약 0.5초, 그다음 수십 ms).
- 서비스가 기록을 남기기 전에 예외로 끝난 실행은 작업의 `last_error` 로 보입니다. 재시작하면 사라집니다.

투자 조언을 제공하지 않습니다.
